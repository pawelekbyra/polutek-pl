### 4.1 Patron Status Source of Truth

**`PatronGrant` table is the sole source of patron/supporter bookkeeping** and **never gates video access** (see §4.4). Owner decision 2026-10-03, "wpłacił = patron": **every** successful tip marks the payer (no amount threshold); one active STRIPE_TIP grant per user is enough. A refund or dispute of one tip removes the marker only when no other paid, not fully refunded tip remains (`lib/modules/payments/application/supporter-grant.ts`); ADMIN/LEGACY/MIGRATION grants are never revoked there. A revocation writes `revokedAt`/`revokeReason`/`revokedById`, never the grant's own `reason`. Owner decision 2026-10-04: a tip gives **no public benefit, not even a badge**; supporter status is visible only to the admin (the payer only sees the thank-you after their own tip). Never put it in public DTOs, `/api/user/profile`, the sidebar layout (`viewerState` has no PATRON) or UI copy. Admin reads (diagnostics, filters, email audience) query:

```prisma
patronGrants: { some: { revokedAt: null } }
```

- `User.isPatron`, `User.patronSince`, `User.patronSource` fields **do not exist** (removed in migration `20260630000000_remove_legacy_user_patron_cache`).
- Never write patron status to the `User` table. Never read it from there.
- `recalculatePatronStatus()` is a pure read — it computes status from active grants, no writes.
- DTO/UI fields named `isPatron` may exist only as derived/decorative values computed from grants or admin role.
- **Do not reintroduce a `PatronGrant`/`getPatronStatus()` check inside `checkVideoAccess()`** without an explicit owner decision to revert the 2026-09-22 non-commercial model — that would silently repaywall content the current Regulamin promises is free.

### 4.2 Payment Lifecycle

```txt
SupportModal amount step -> POST /api/checkout/create-intent
  -> one Payment(PENDING) + one PaymentIntent per tip attempt (client requestId, kept in
     sessionStorage; a changed amount/currency UPDATES that intent, it never opens a new one)
Stripe confirm (in the gate) -> payment succeeded at Stripe
  -> fulfillPayment(), from whichever arrives first, all replay-safe:
       webhook payment_intent.succeeded | GET /api/payments/[id] fast path | cron
       -> CAS PENDING|FAILED|CANCELED -> SUCCEEDED (Stripe's `succeeded` with checked amount,
          currency, intent and user is the source of truth)
       -> supporter marker (PatronGrant STRIPE_TIP) if none is active
       -> after the commit: thank-you e-mail + notification (never inside the transaction)
```

`fulfillPayment()` in `lib/modules/payments/` is idempotent and replay-safe. Always use it for payment fulfillment, never issue manual `updateMany({ status: 'SUCCEEDED' })` shortcuts. `payment_intent.payment_failed` is one failed **attempt**: the payment stays PENDING (the intent returns to `requires_payment_method` and a later attempt can succeed). Unpaid tips are closed by the reconciliation cron after 24 h (intent canceled in Stripe, row CANCELED). The webhook (`handleStripeWebhook`) verifies the signature on the raw body with `Stripe.webhooks.constructEvent`, logs every received and rejected event (ids and types only), ignores events whose `livemode` differs from the secret key's mode and `succeeded` intents without `metadata.paymentId` (200), and returns non-2xx only when Stripe should retry. Disputes are resolved from the dispute's current status read from Stripe at handling time (events can arrive out of order). Admin refunds use an idempotency key and are always audited in `adminRefund`.

**Return-page fast path (added 2026-07-21):** the webhook remains the reliability backbone, but `getOwnedPaymentStatus()` (`lib/modules/payments/application/get-payment-status.use-case.ts`, backing `GET /api/payments/[paymentId]`) no longer only reads the local `Payment.status`. When the caller's own payment (ownership already enforced by the `{ id, userId }` lookup) is still `PENDING` and has a `stripeIntentId`, it retrieves that PaymentIntent directly from Stripe and, if Stripe already reports `succeeded`, calls `fulfillPayment()` right there — the same canonical, replay-safe path, never a manual status write — before responding. It also re-checks FAILED/CANCELED rows (a tip may have succeeded on a later attempt). This is what lets the tip gate's thank-you screen resolve near-instantly instead of only after the webhook lands; the polling loop there does an immediate check on mount rather than waiting for the first interval tick. Any Stripe/network failure in this path is swallowed and falls back to the normal webhook-driven polling — it is a best-effort fast path, not a new source of truth.

**Return-page message trusts Stripe's redirect signal.** `useCheckoutFlow` (used by `SupportModal`) reads Stripe's own `redirect_status` off the return URL: `succeeded` (or the param being absent on a plain card confirmation) shows the full thank-you immediately; `failed` shows the failure screen (`TipThanksStep`; UI statuses are `PROCESSING | SUCCEEDED | FAILED | REFUNDED`, there is no "access" state); genuinely async `pending`/`processing` methods get a neutral processing screen until the background reconciliation confirms. The reconciliation loop only ever *upgrades* a processing screen to success — it must never downgrade an already-shown success message, and no raw `PaymentUiStatus` enum or "webhook" jargon may reach the UI. Closing the success screen (X or "back to site") after a succeeded payment does a full `window.location` reload to the clean URL so every server-rendered surface (e.g. the Patron badge) comes back fresh at once — do not downgrade this to a soft `router.replace`, which leaves stale non-patron server state and cached playback plans.

### 4.3 Video Playback Security

- **Never expose `videoUrl` to the public frontend.** Use `PublicVideoDTO` for all public-facing data.
- The only playback path is the own-HLS plan from `/api/media-source/[videoId]` (`PlaybackService` → `buildSelfHlsPlan()`). The old `/api/media/[...path]` proxy, `Video.videoUrl` playback, embeds (YouTube/Vimeo) and provider signing (Mux/Cloudflare Stream) no longer exist; `Video.videoUrl` is a dead legacy column that nothing reads or writes. `MediaPolicy.isProbablyRawMediaUrl()` stays as a safety net: a raw storage/provider URL in a plan is dropped by `/api/media-source` (plan becomes not playable).
- `PlaybackPlan` from the access module gates all player mounting: `READY` → mount player, any denied state → locked placeholder.
- Never mount a player, fetch streams, request tokens, resolve the playback source, or log views for a denied plan.
- Rows of any provider other than `SELF_HLS` (leftover Mux/Cloudflare Stream/YouTube/Vimeo/R2/S3/Blob assets or routes) are ignored by `PlaybackService` (never crash, never played, no URL/id in the plan); publication blockers (`VideoPolicy`) and `VideoPlaybackRouteService.activateRoute()` accept only `SELF_HLS`.
- **Never CDN-cache `/api/media-source` responses** (no `s-maxage`/`public` Cache-Control). The response carries a per-viewer `playbackSessionId` bound to the requester fingerprint.

### 4.4 Access Checks

### 4.9 Comment Reactions

- `CommentReactionType` enum is `LIKE | DISLIKE` (one reaction per user per comment via `@@unique([userId, commentId])`).
- Dislike has **no public counter** — only `likesCount` is aggregated; deleting/replacing a DISLIKE must never touch `likesCount`.
- Reactions are a target state, not a toggle: `setCommentReaction` / `setVideoReaction` (`LIKE`, `DISLIKE` or `null`), idempotent and race-safe (`createMany({ skipDuplicates })`, counters move by affected row counts). API: `PUT /api/comments/[id]/reaction` with optional body `{ type: "LIKE" | "DISLIKE" }`, `DELETE` clears (60/min per user). Video likes: server action `setVideoReaction` in `lib/actions/interactions.ts`, which must never `revalidatePath` (Hero updates its own state from the result).
- Visibility: `mapCommentToDto` is a whitelist. Text and author are returned only for `VISIBLE`; moderators also see `HIDDEN`/`HELD_FOR_REVIEW`; `DELETED` content stays in the database but is shown only in the admin panel and never when the author deleted it; the text of author-deleted comments is erased after 30 days by `/api/cron/purge-deleted-comments` (moderation-deleted/hidden text is kept). `threadCommentWhere()` in the repository is the one list filter (also hides comments of deleted accounts). `repliesCount` in DTOs is computed (`_count`), the `Comment.repliesCount`/`score`/`imageUrl` columns are no longer read or written.
- No supporter ("Patron") distinction anywhere public (owner decision 2026-10-04: a tip buys nothing, not even a badge): comment DTOs carry only `ADMIN`/`AUTHOR` badges, the UI shows only "Twórca" (video creator), no avatar ring. Patron status is visible in the admin panel only.
- Moderation is a state machine in `CommentPolicy` (`restore` only from `HIDDEN`/`HELD_FOR_REVIEW`; `DELETED` is final); a disallowed action is `CONFLICT` (409). Every comments route maps errors through `commentErrorStatus` / `lib/api/comment-response.ts`; database messages never reach the client (`commentDatabaseError`).
- Reports: one per user and comment; `reportsCount` = pending reports (recomputed on report and on resolve); 3 pending reports hold a viewer's comment for review, never one by an admin or the video's creator.
- Threads: the list embeds the first 3 replies; the rest is paged through `GET /api/comments/[id]/replies` (public, also for guests).

### 4.10 Tip Gate (SupportModal), One Payment Path

The only way to tip is the step-by-step tip gate `app/components/channel/SupportModal.tsx` (+ `app/components/support/*`), opened by the `polutek:open-support` window event (Hero's "Wspieraj", `AccessLockOverlay`), handled in `ChannelHome`. Signed-out clicks open sign-in first. `ChannelHome` also opens it on load for signed-in viewers on `?support=1` (stripped at once) and on a Stripe redirect return (`?success=true&payment_id=...`, lands on the thank-you step; `UrlMask` preserves `success`/`payment_id` until then). It is mounted only while open, and Stripe.js is loaded lazily from there (`lib/payments/stripe-browser.ts`, `@stripe/stripe-js/pure`): visitors who never open the gate download nothing from Stripe. Never add a module-level `loadStripe()`.

Steps (`STEPS`): recipient (with the Terms/Privacy consent checkbox, `TipRecipientStep`; the consent is not stored on the server, an open owner question) -> disclaimer ("a tip unlocks nothing") -> amount (currency from `detectDefaultCurrency`, free amount, minimum from `/api/payment-settings`) -> method -> that method's form -> thank-you. The amount step creates or updates the attempt's PaymentIntent (§4.2); the method tiles come from its `payment_method_types` (`getTipMethodTiles()` in `tip-flow-config.ts`) plus Apple Pay / Google Pay when the device has one, and a "Crypto" placeholder that never takes money. Each method confirms on the same intent with its own Stripe.js call (`TipPayStep.tsx`: BLIK, P24 redirect, card, wallets via `ExpressCheckoutElement`, others via a single-method `PaymentElement`); a ref guards against double confirms. The intent description is built on the server (`tipIntentDescription()`, "Napiwek dla {APP_NAME}"), never taken from the client. Client code must use `APP_NAME`, not `MAIN_CREATOR_NAME` (not a `NEXT_PUBLIC_` variable). Look: canary-yellow surface (`--chan-gold`) with black accents (`.tip-gate-surface` in `globals.css`), fixed 440 x min(640px, 90dvh) window on desktop, full screen on phones; the frame never changes size between steps; Regulamin/Polityka open in `TipLegalDialog` on top of the gate.

**One minimum per currency.** `PaymentCurrencySetting.minAmountMinor`, set in `/admin/payments`, is the minimum the gate shows and the server enforces (`getPaymentCurrencyLimits()`, `GET /api/payment-settings` -> `{ limits }`). The legacy columns `patronThresholdMinor` (dead) and `patronBoxMinMinor` (counts as max(min, boxMin) until the next admin save clears it) are to be dropped in a cleanup migration. Stripe Elements render in the viewer's language.

### 4.12 Auth: Better Auth (2026-10-02, replaces Clerk)

Full write-up: `docs/architecture/auth-better-auth.md`. Rules to keep:

- **Library and data.** `better-auth` with the Prisma adapter on our Postgres. Our `User` model is the Better Auth user (`name` = nickname, `image` <-> `imageUrl`, plus `emailVerified`, `twoFactorEnabled`, `onboardingPending`); extra tables `Session`, `Account`, `Verification`, `TwoFactor` (migration `20261002100000_add_better_auth`, additive). `ClerkEvent` is a dead table kept only because migrations are additive. The `admin` plugin is deliberately not used; roles stay `User.role`.
- **One identity entry point.** Server: `lib/auth/server.ts` (`auth()`, `getAuth(req)`, `currentUser()`) and `lib/api/auth.ts` (`getActorFromAuth`, `requireAdminActor`: DB-backed actor, soft-deleted users rejected). Client: `lib/auth/client.ts` (`authClient`) and `lib/auth/react.ts` (`useAuth`, `useUser`, same shape the components used). Do not import `better-auth` anywhere else in app code; do not add a second get-or-create-user path (Better Auth creates the row; `getOrCreateCurrentUser()` only loads it and fails closed).
- **Admin** = `User.role = ADMIN`. Bootstrap by `ADMIN_EMAILS` (a verified e-mail is promoted on actor resolution, audited as `AUTH_ADMIN_BOOTSTRAP`; a never-verified address is never promoted). The check runs on every request, so empty the variable after the first sign-in (a demotion is otherwise undone) and never list a shared inbox. `ADMIN_CLERK_USER_IDS` is gone.
- **Methods.** E-mail + password (min 10 chars, no composition rules, haveIBeenPwned in production, `requireEmailVerification`, `autoSignIn` off; sign-up with an existing e-mail answers `EMAIL_TAKEN`, see below), Google (redirect + One Tap, `account.accountLinking.trustedProviders: ["google"]` so a Google sign-in links to the existing row with the same e-mail), TOTP two-step (`twoFactor`), passkeys (`@better-auth/passkey`, RP ID `pawelperfect.com`, origins www + apex from `getPasskeyRelyingParty()`; added from the account panel with a fresh session, or "Użyj klucza dostępu" creates the account like Google: passkey-first sign-up in `lib/auth/passkey-signup.ts`, signed token after e-mail + Turnstile, account created after the ceremony, signs in only after the e-mail link; user verification enforced; a passkey sign-in, like Google, gets no TOTP step; logic in `lib/auth/passkey.ts`). Apple is not offered.
- **Existing e-mail at sign-up (owner decision 2026-10-02: convenience over privacy, enumeration accepted).** Sign-up with an address that already has an account returns 422 `EMAIL_TAKEN` (`EMAIL_TAKEN_GOOGLE` if it only has a Google link); the modal shows "this e-mail already has an account" with Sign in / Forgot password actions. Implemented as an AFTER hook (`rejectExistingEmailSignUp` in `lib/auth/hooks.ts`) because `options.hooks.before` runs before the captcha plugin; do not move it to a before hook, or Turnstile is bypassed. Sign-in and password reset stay enumeration-safe. The "account exists" e-mail was removed.
- **Protection.** Cloudflare Turnstile on sign-up/sign-in/reset/resend (`CAPTCHA_ENDPOINTS` in `lib/auth/config.ts`; the widget gets its site key at runtime through `AuthPublicConfigProvider` and renders `interaction-only`: the check starts when the form opens, invisible and out of layout unless a challenge is needed; submit buttons stay active, `useCaptchaGate` queues an early click until the token arrives, 15 s limit with "try again"); Better Auth rate limits on our Redis REST store via `customStorage.consume` (`lib/auth/rate-limit-storage.ts`) plus a per-e-mail sign-in lockout (10 per 15 min); secure/HttpOnly/SameSite=Lax cookies with prefix `pp`; password change and reset revoke other sessions; audit events `AUTH_SIGN_UP/IN/OUT`, `AUTH_PASSWORD_CHANGED`, `AUTH_ADMIN_BOOTSTRAP`, `AUTH_PASSKEY_ADDED/REMOVED/SIGN_IN`, `USER_NICKNAME_CHANGED` (ids only, never secrets).
- **Pre-hijack guard.** If a verified provider is linked to an account whose e-mail was never verified, its password, passkeys and sessions are deleted (`beforeAccountCreate` in `lib/auth/hooks.ts`); a password reset on a never-verified account drops its passkeys (`onPasswordReset`). Keep it. Google linking is allowed onto an unverified row (`requireLocalEmailVerified: false`, audit F-04) precisely because of this guard; never-verified password sign-ups are pruned after 7 days by `/api/cron/prune-unverified-accounts`.
- **Audit follow-ups (2026-10-02, `docs/audit/2026-10-02-auth-flows-audit.md`).** Return path `?next=` works (same-site relative paths only); verification-link results are shown (`?verified=1` / `?error=TOKEN_EXPIRED|INVALID_TOKEN`, handled in `AuthModalProvider`); sign-in lockout counts only failed attempts keyed per e-mail + IP; `freshAge` stays 1 day and stale sessions get a "sign in again" prompt (`SESSION_NOT_FRESH`); "remember this device" for 2FA is opt-in (7 days) and 2FA does not apply to Google/One Tap (decision); backup codes can be regenerated; One Tap (and Google's script and `g_state` cookie) loads only inside the open sign-in window (`SignUpFooter` → `GoogleOneTapPrompt`), never for a visitor who just browses; account deletion needs the password (or a Google sign-in from the last 10 min) and refuses to delete the last admin; legacy accounts with a missing/invalid/duplicate nickname go through onboarding at next sign-in.
- **Proxy.** `middleware.ts` has no auth library call: it keeps the public-route list, CSRF (`/api/admin/*` and `/api/user/*`), admin rate limits, the cron/webhook exemptions and the CSP, and gates the rest with an optimistic session-cookie check (`getSessionCookie`). Missing cookie: API paths get JSON 401, pages are redirected to `/?signin=1&next=...` (the modal opens). The cookie is never proof of identity; real validation is in server code. `/api/auth(.*)`, `/reset-password` and `/sso-callback` are public and exempt from the `/pl` rewrite.
- **Nickname.** Chosen only in the first-sign-in dialog (never in the sign-up form): 3-30 chars (`lib/auth/nickname.ts`), checked for case-insensitive uniqueness by `GET /api/users/nickname-available` (public, per-IP limited) and again server-side (`completeOnboarding`, `updateNickname`). The database enforces it for active, onboarded accounts (partial unique index `User_name_lower_active_key` on `lower(name)`, migration `20261003200000`; a lost race answers `NICKNAME_TAKEN`). Placeholders of accounts in onboarding reserve nothing, and such an account cannot comment or react (`Actor.onboardingPending`, `CommentPolicy`, code `ONBOARDING_REQUIRED`). Edits go through `PATCH /api/user/nickname`; Better Auth's `/update-user` is disabled.
- **Avatar.** New accounts get `public/default-avatar.jpg` (also for Google users, by design). A chosen file is resized to 256 px in the browser (`lib/auth/avatar-client.ts`), validated server side (`validateAvatarDataUrl`) and stored as bytes in the `UserAvatar` table; `User.imageUrl` points at the public `/api/avatars/[userId]?v=...` route (`PUT /api/user/avatar`; `SafeAvatar` renders it unoptimized). Legacy rows may still reference `img.clerk.com`, which stays in the CSP `img-src`.
- **First sign-in (Google and e-mail).** Every new account gets a placeholder name (e-mail local part) and `onboardingPending = true`; `OnboardingDialog` (mounted in `AuthModalProvider`, cannot be dismissed) asks for the nickname and an optional avatar, then `POST /api/user/first-sign-in` sets them and sends the welcome e-mail. This is the only place the welcome e-mail is sent (exactly once). The sign-up form asks e-mail, password and "Repeat password" only.
- **E-mails.** Verification, reset and password-changed mails go through the existing Resend module and `EMAIL_DEFAULTS`/`EmailTemplate` (slugs `verify-email`, `reset-password`, `password-changed`, `welcome-email`, and for an e-mail change `change-email-confirm`, `change-email-verify`, `email-changed`), localized by `User.language`, without a marketing unsubscribe link, fire-and-forget (no timing leak). A DB template saved in `/admin/emails` wins over the default.
- **E-mail change.** Needs the password (or a Google sign-in from the last 10 min) in the `/change-email` body (`guardChangeEmail` before hook, 5/h per user), is approved from the CURRENT address first, then verified on the new one, and the old address is notified (`AUTH_EMAIL_CHANGED`). Reset/verification mails are also limited per target address. Auth rate-limit counters fail open with an error log when Redis is down (1.5 s timeout), a deliberate choice documented in `lib/auth/rate-limit-storage.ts`.
- **Return pages.** `/sso-callback` (Google return: must never render blank, 8 s fallback link; return path in `sessionStorage` via `lib/auth/sso-return.ts`) and `/reset-password` (e-mail link target, `?token=` or `?error=INVALID_TOKEN`).
- **Language.** Stored in `User.language` (the database is the only copy); `AuthLifecycleProvider` syncs it once per login and persists changes through `PATCH /api/user/language`.
- **Account deletion.** `DELETE /api/user/account`: our anonymising cleanup, then sessions/accounts/two-factor/passkey rows are deleted; the row stays as a tombstone (`deleted_…@deleted.invalid`) and cannot sign in again. The cleanup also erases the text/image of all the user's comments (rows stay as author-deleted, threads intact), removes the address from `BroadcastEmailRecipient`/`EmailEvent` (pending broadcast rows become SKIPPED), and queues the Resend Audience contact in `ResendContactRemoval` (tried at once with a 5 s cap, then retried by `/api/cron/retention`). `Payment` and `AuditLog` rows are not touched.
- **Terms acceptance.** `User.termsAcceptedAt`/`termsVersion` (version = `LEGAL_DOCUMENTS_VERSION` in `lib/legal/version.ts`, the documents' effective date, from which `LEGAL_EFFECTIVE_DATE` is derived): stamped by `beforeUserCreate` (the sign-in window shows the Terms/Privacy notice next to every way to sign up) and by `create-intent` when the tip gate's Terms box was ticked (`recordTermsAcceptance`). Change the version whenever a legal document changes.
- **Privacy retention.** `/api/cron/prune-expired-auth` (daily) deletes expired `Session`/`Verification` rows; `/api/cron/retention` (daily) clears IP/user agent (and their hashes) older than `TECHNICAL_DATA_RETENTION_DAYS` (90, `lib/modules/privacy/domain/retention.ts`, stated in the Privacy Policy and checked by `legal-docs-consistency.test.ts`) in `AuditLog`, `Session`, `VideoPlaybackSession`, `VideoView` without deleting rows. Client IP/UA hashes are HMAC (`clientFingerprint` in `lib/modules/privacy`), key `IP_HASH_SECRET` or derived from `BETTER_AUTH_SECRET`.
- **Secrets.** `BETTER_AUTH_SECRET` (>= 32 chars, required in production; rotating it signs everyone out and breaks stored TOTP secrets AND backup codes, so 2FA accounts are locked out: follow the procedure in `docs/architecture/auth-better-auth.md`), `GOOGLE_CLIENT_ID/SECRET`, `TURNSTILE_SITE_KEY/SECRET_KEY`, `ADMIN_EMAILS`, optional `BETTER_AUTH_URL`, `BETTER_AUTH_TRUSTED_ORIGINS`. Google redirect URI per host: `<origin>/api/auth/callback/google`.

### 4.13 Public App Shell, Preload and Install UX

- The root public experience should render app shell immediately; no blocking splash/ENTER gate (nothing the viewer has to click through).
- **Update 2026-09-30:** the statement above and the "It is **not** a click gate … `PAGE_REVEAL_MAX_WAIT_MS` (3s …)" sentence in the next bullet are historical; the current behavior (click-through rabbit gate, 6 s max wait before it appears) is described in the "Current UI/runtime baseline" section near the top of this file.
- **Update 2026-09-26 (coordinated first reveal — fixes the "popcorn"/twinkling load):** the home page used to pop in piece by piece (navbar auth skeleton, sidebar skeleton → client fetch, player loader card, comments skeleton), each on its own schedule. Now:
  - `PageRevealGate` (`app/components/preload/PageRevealGate.tsx`, wrapped around the page in `HomeExperience.tsx`) keeps one calm full-screen `SitePreloaderScreen` (glasses logo + thin bar) on top of the already-rendered page until auth `isLoaded` and the `player`/`comments` pieces report settled via `usePageRevealReady(key, ready)` (`revealKey="player"` from `Hero`, and `EmbeddedComments`), then fades the whole page in at once. `player` means the player is already in its final visible state, not just that access was granted: when the player mounts, `PremiumWrapper` stays silent and `VideoPlayer` reports once playback has *settled* — a real frame is on screen (`playing`/`timeupdate > 0`), or, when autoplay is off or blocked (`onAutoPlayFail`), the stream `canplay`s — or on an error/timeout state; locks, coming-soon and error overlays are reported by `PremiumWrapper` itself. The hero autoplays (muted, `preload="auto"`) under the preloader, so the page is revealed on an already-playing, stable player (the viewer may miss a fraction of a second of the muted start; that was accepted to remove the post-reveal poster→video switch). The start-up overlay hides on the first *rendered* frame, not on Vidstack's `play` event (`play` fires before any frame is painted). Once the media `canplay`s it also drops its delayed spinner (`PlayerStartLoading`'s `ready`). It is **not** a click gate: it always leaves after `PAGE_REVEAL_MAX_WAIT_MS` (3s from navigation start, at least 0.7s after a late hydration), CSS hides it after 6s even without JS, and later mounts in the same document skip it. Don't add new `waitFor` keys for below-the-fold or slow things — the max wait would just hide them behind the preloader.
  - `app/[locale]/(home)/loading.tsx` renders the same `SitePreloaderScreen` on a first load (via `HomeRouteLoading`, see below), so "server streaming" and "client settling" read as one continuous screen.
  - **Update 2026-10-04 (first view complete from the server):** `HomeExperience` also hands the browser the viewer's session (`AuthSessionSeedProvider` in `lib/auth/react.ts`, snapshot from `lib/auth/session-snapshot.ts`: no token; `useAuth`/`useUser` answer from it until Better Auth's own client has answered once, then never again), the first page of comments (`initialComments`, seeded into the TanStack query) and the hero's playback plan, so the navbar, locks, likes, comments and the player are final in the first HTML. Relative dates and the premiere countdown use the server render time during hydration (`app/components/RenderClock.tsx`); numbers and dates use a fixed locale and `Europe/Warsaw`. `auth()`, the home content, the main-channel row and the admin avatar are read once per request (React `cache`). The page stays `force-dynamic` + `no-store`: never put it (or anything with the session, comments' viewer data or a plan) in a shared cache. Switching video keeps the previous comments dimmed (`keepPreviousData`), and the sidebar keeps its layout during a refetch.
  - The sidebar layout is built server-side in `HomeExperience` (`ChannelLayoutService.getSidebarLayout`, JSON round-tripped to the `/api/channel/sidebar` shape) and passed down as `initialLayout`/`initialLayoutViewerKey`; `SidebarPlaylist` skips its first fetch when the client viewer key matches, and still refetches on any auth change or if the server load failed (null). This also removes one `/api/channel/sidebar` call per page view.
  - **No cover image in the player (owner decision 2026-10-04):** covers belong to thumbnails, the playlist, cards and metadata only. Before the plan, before the player mounts and until the first real frame, `PremiumWrapper` and `VideoPlayer` show `PlayerStartLoading`: the player's own black frame with a spinner that fades in only after ~450 ms; the overlay fades out on the first real frame. The player gets no `poster`. Tests: `video-player-page-reveal`.
  - **Sound:** a video picked with a click/tap in the playlist (`ChannelHome.handleVideoSelect` sets `startWithSound`, passed Hero → `VideoPlayer`) starts unmuted; the first video and Back/Forward start muted. The gate click (`polutek:gate-enter`) unmutes the hero (and starts it if even muted autoplay was refused). If the browser refuses sound (`onAutoPlayFail` with `muted: false`), the player restarts muted and shows the `UnmuteHint` button; it also shows whenever a video plays muted that the viewer did not mute. Such a video (e.g. after a reload, where the gate is skipped and there is no gesture yet) is also unmuted by the viewer's first gesture anywhere on the page (`player/useUnmuteOnFirstGesture.ts`: one-shot capture listener on pointerdown/pointerup/touchend/keydown, skips the hint, the player's volume control and the "m" key, never saved as a choice). The viewer's own mute (mute button, "m", or unmuting via slider/hint) is kept for the tab in sessionStorage (`player/sound-preference.ts`) and wins over `startWithSound`.
  - **First seconds warmed on intent:** pointer enter/focus on a playlist tile (`SidebarPlaylist`) warms the plan, the first page of comments and, through `preload/media-warmup.ts`, the stream's first seconds: a throw-away hls.js with the player's config (same start rung, same player-size cap, detached muted media element) loads master, media playlist, init and the first segment, then stops; the click then hits the HTTP cache (same plan, same URLs). Bounded: 150 ms dwell, at most 2 at once (oldest cancelled), 15 s timeout, once per stream, cancelled on pointer leave or when another video is picked, nothing on Data Saver/2g/3g, touch only on a known 4g connection. It gets only a READY plan's URL, calls no API, opens no session and counts no view (the intent plan request itself opens a session row, as before). The idle warm-up of nearby videos (comments only, no plan/media) is skipped on constrained networks.
- **Update 2026-09-26 (in-session switches never re-render the page on the server):** on the home page nothing in-session may use `router.push`/`router.replace`/`<Link>` navigation to change `?v=` or other query params. Those are real navigations: the server re-renders the whole `force-dynamic` page and the route's `loading.tsx` fallback replaces the UI (it re-showed the preloader on every video click). Instead:
  - **Video switch:** `SidebarPlaylist`'s link `preventDefault`s plain left clicks (modified and middle clicks still open the real link) and `ChannelHome.handleVideoSelect` switches locally, then calls `window.history.pushState({ polutekVideoId }, "", "?v=<slug>")`. Next.js 16 patches `pushState`/`replaceState` so `useSearchParams` and later refreshes follow the new URL without a server fetch. A `popstate` listener restores the video recorded in the history entry (`UrlMask` rewrites the visible URL to `/`, so the URL alone can't be trusted on Back).
  - **Like state:** the server renders the viewer's like/dislike only for the video it opened with. `ChannelHome` passes `initialInteraction` only for that video; for any other, `Hero` fetches `GET /api/videos/[id]/viewer-state` (`private, no-store`).
  - **Loading screen:** `app/[locale]/(home)/loading.tsx` renders `HomeRouteLoading`: the full `SitePreloaderScreen` only on the first load of the document, and `HomePageSkeleton` for later in-app navigations back to home (e.g. from a legal page), so the branded preloader never re-appears mid-session.
  - **Player handoff:** `VideoPlayer`'s pre-mount frame renders the same `PlayerStartLoading` frame instead of `null`, so the handoff from `PremiumWrapper` to the mounted player never flashes.
- `AppPreloadProvider` is the current in-memory preload layer for playback plans, the first seconds of streams and comments.
- `ServiceWorkerCleanup` disables persistent service-worker interception/caches. Do not add offline/persistent caching for auth, payments, media-source, playback, or user-specific data without a focused design.

An upcoming video may be the Hero.

### 4.17 Own HLS delivery: the only video source (2026-10-02)

`StorageProvider.SELF_HLS` plays video from our own HLS: encoded by `scripts/hls/encode-hls.mjs`, stored in the private R2 bucket `polutek-hls`, delivered by the Cloudflare Worker `workers/hls-edge` on `video.pawelperfect.com` (Free plan). Rules: the delivery token (`SelfHlsTokenService`, HMAC over `<videoId>/<version>/<exp>`, in the URL path) is issued **only** by `PlaybackService` after `checkVideoAccess()` and the premiere gate, via `buildSelfHlsPlan()`; a denied plan carries no URL (tested). There is no fallback to another provider: without `HLS_TOKEN_SECRET`, or when the own-HLS asset is not READY, the plan is `ERROR`/`PROCESSING`/`NO_PRIMARY_ASSET` with no URL, token or session, and `VideoPlayer` plays only `source.kind = self_hls` (an https `.m3u8`). Manual route activation: `scripts/hls/activate-self-hls.sql` (normally the worker does it). It is access control, not DRM. **All three videos (`czesc`, `jj`, `dla-patronow`) are served from own HLS.** Player: hls.js is a pinned npm dependency (`hls.js/light`) loaded from our own bundle via `provider.library` (`app/components/player/self-hls.ts`); never the Vidstack CDN default, no `cdn.jsdelivr.net` in CSP. Token renewal never remounts the player: `PremiumWrapper.renewPlaybackPlan()` re-fetches `/api/media-source/<id>?session=<id>` (full access check; the server keeps the viewer's own playback session) and hls.js rewrites every request to the newest token (`xhrSetup`). The old provider routes (`PREVIOUS`) and the other legacy rows stay in the DB and are ignored by the code (deleting them is a separate cleanup PR). The `StorageProvider` enum values other than `SELF_HLS` and the tables `VideoDistributionPlan/Target`, `VideoProviderJob`, `VideoProviderWebhookEvent` are LEGACY in `schema.prisma` (migration history stays additive; do not drop them without an owner decision, do not write them). Details: `docs/operations/HLS-SELF-HOSTED.md`, `docs/architecture/self-hosted-hls.md`.

**Own upload + encode pipeline (2026-10-03):** decision 2026-10-02: no third-party video providers (Mux, Cloudflare Stream, Vimeo, YouTube); `SELF_HLS` is the only source (the provider code — Mux, Cloudflare Stream, YouTube, Vimeo, distribution plans/jobs, webhooks, reconcile cron, `/api/media` proxy — was removed on 2026-10-02; never reintroduce a second provider without an explicit owner decision). Admin uploads the ORIGINAL straight to the private R2 bucket `polutek` (presigned multipart, resumable; server verifies size and magic bytes at `complete`, deletes bad files), `completeOriginalMultipart` queues a `VideoEncodeJob` (Postgres, `SELECT ... FOR UPDATE SKIP LOCKED`, one encode at a time, retries with backoff, heartbeat, cancel, re-encode; no pg-boss/Redis). The worker is the separate container `encoder` (`scripts/video-worker.ts`, `lib/modules/video-pipeline/`, image target `worker`): download, ffprobe limits, `encodeHls()`, upload to `polutek-hls` with `master.m3u8` last, verify, only then `VideoAsset(SELF_HLS, READY)` + active route + optional auto-publish; failures/cancel delete the partial prefix. Never run encoding in the Next.js request path. Publication blockers accept only `SELF_HLS`. Everything (flows, ops, debugging, rollback, server enable commands): `docs/operations/VIDEO-PIPELINE.md`.

**Update 2026-09-30 (admin hardening, "Etap 0", PRs #1528/#1529/#1530):** the admin (identity layer since 2026-10-02: Better Auth, see 4.12; the break-glass health route and `?token=` rules below are historical) was hardened without changing its architecture. Rules future agents must keep:
- **CSRF:** every POST/PUT/PATCH/DELETE under `/api/admin` is checked centrally in `middleware.ts` via `lib/api/csrf.ts` (`assertSameOrigin`), before `auth.protect()`. If `Origin` is present its host must equal the request host or a host derived from `NEXT_PUBLIC_APP_URL` (www and apex); if `Origin` is absent, only a missing/`same-origin`/`none` `Sec-Fetch-Site` passes. Rejections are 403 `{error:"Forbidden"}`. Emergency switch: env `ADMIN_CSRF_MODE=report` (log only). No custom header is required, so the existing admin UI needs no changes.
- **Rate limits:** `lib/api/admin-rate-limit.ts`, run in the same middleware after auth, keyed by admin user id and IP (Upstash; both checks in parallel, 700 ms timeout, fails open on error/timeout). Defaults 120/min for reads and mutations; strict limits: refund 5, dispute-sync 5, emails/broadcast 3, emails/broadcast/test 5, notifications/broadcast 3, users/[id]/patron 10, payment-settings 10. Bulk moderation on `/admin/comments` fires up to 50 POSTs at once, so do not lower the default mutation limit below that.
- **Body validation:** admin mutation routes read bodies through `parseAdminBody` (`lib/api/admin-body.ts`) with zod schemas in `lib/api/admin-schemas.ts` (400 `{error, details}`, unknown fields stripped). `allowEmpty` accepts only a truly empty body: malformed JSON is 400 (the refund route treats an empty body as a full refund, so a truncated body must never be read as empty). `tests/unit/admin-mutations-validation-static.test.ts` requires a schema (or a documented allowlist entry) for every mutating admin route.

### 5.2 Shared admin list-query scaffold (2026-09-26)

Resolved (partially — see the videos exception below) `ADMIN-LIST-SCAFFOLD-CONSOLIDATION-001`. `lib/admin/use-admin-list-query.ts` is a shared client-side hook (`useAdminListQuery<TItem>()`) that owns the page/total/totalPages/items/isLoading/error state and the fetch-try-catch-parse-error boilerplate that used to be independently duplicated across list pages. It deliberately does **not** own filter state or URL construction — each page keeps its own filter state and builds its own request URL, then calls the hook's `fetchPage(url, targetPage, { fallbackMessage })`; the hook returns the raw parsed response body on success so callers can pull out page-specific extra fields (stats, summary) themselves. This narrow scope (state/fetch bookkeeping only, not a full data-table component) was a deliberate choice to keep the migration low-risk given the "no list may lose existing functionality" constraint — no API contract changed.

Migrated to `useAdminListQuery`: `app/admin/comments/reports/page.tsx`, `app/admin/comments/page.tsx` (search/videoId filters and bulk-selection state stayed local), `app/admin/users/page.tsx` (all its filters stayed local; a stray no-op `setPage(1)` call on the patron-source filter was removed as dead code — the page-1 reset already happens via the filter-change `useEffect` calling `fetchUsers(1)`).

**`app/admin/videos/components/useAdminVideos.ts` was deliberately NOT migrated.** Its `fetchVideos()` has three behaviors the generic hook doesn't (and shouldn't be extended to) support: (1) a 401/403 response sets a distinct "Brak uprawnień administratora." message rather than the generic load-error fallback — the shared hook only sees `res.ok`, not the status code; (2) `stats` is extracted from the same response body and stored separately; (3) `isRefetching` is only set around calls that explicitly pass `{ pending: true }` (initial load and background/no-pending calls leave it `false`), which `VideoTableWrapper.tsx` relies on to distinguish the initial full-skeleton state from a background refetch overlay — the shared hook's `isLoading` is unconditionally true for every call, which would have made both states fire together on first load. Reusing the hook here would have meant either losing one of these three behaviors or extending the hook with video-specific escape hatches, both of which cut against the hook's whole point. `useAdminVideos` already is videos' single, non-duplicated list/fetch implementation (nothing else reimplements it), so there was no duplication left to consolidate there — only `readVideoLoadError` (see below) was actually duplicated code, and that's fixed.

**`readVideoLoadError`/`readAdminApiError` duplicate merged**: the local `readVideoLoadError` in `useAdminVideos.ts` was removed; it now imports the shared `readAdminApiError` from `lib/admin/api-error.ts` (moved there via `git mv` from `app/admin/videos/components/api-error.ts`, content unchanged — import paths in `videos/page.tsx`, `videos/[id]/edit/page.tsx`, `videos/[id]/page.tsx` and `tests/unit/admin-api-error.test.ts` updated accordingly).

## 6. Cron Jobs

Registered in `vercel.json` under `crons`. All cron routes live in `app/api/cron/`. Auth via `Authorization: Bearer <CRON_SECRET>` header.

**`stripe-reconciliation`** runs every 15 min from a systemd timer on serwerek (SERWEREK.md §16). It checks every `PENDING` payment older than 15 min (oldest first, 100 per run, any age) against Stripe through `reconcilePaymentWithStripe()`: succeeded -> `fulfillPayment()` (no thank-you e-mail for tips older than 7 days); canceled -> `CANCELED`; unpaid for 24 h -> the intent is canceled in Stripe and the row `CANCELED`. `?scope=recover` also re-checks `FAILED`/`CANCELED` rows (500 per call); run it once by hand after a fix like PAY-01.

**Update 2026-09-29:** `/api/cron/(.*)` is a public route in `middleware.ts` (each handler authorizes itself with `Bearer $CRON_SECRET` and returns 401 when the secret is missing). Before this, the routes were not listed there, so Vercel Cron (no Clerk session) hit `auth.protect()` and got the site's HTML page (HTTP 200) instead of the handler: every cron silently did nothing. `CRON_SECRET` must be set in Vercel Production. `tests/unit/security/cron-routes-reach-handler.test.ts` guards both halves. To check a cron from outside: without the token it must return 401 JSON, not HTML.

| Route | Schedule (Pro) | Purpose |
|---|---|---|
| `/api/cron/stripe-reconciliation` | `*/15 * * * *` | Records tips Stripe reports as succeeded (`fulfillPayment()`), cancels abandoned ones (see above) |
| `/api/cron/prune-playback-sessions` | `0 5 * * *` (registered; daily works on Hobby) | Deletes `VideoPlaybackSession` rows older than 30 days that were never counted as a view (`pruneStalePlaybackSessions()`, `lib/modules/video/`) |
| `/api/cron/purge-deleted-comments` | `15 5 * * *` (systemd timer on serwerek) | Erases the text of comments their authors deleted more than 30 days ago (`purgeAuthorDeletedComments()`, `lib/modules/comments/`) |
| `/api/cron/prune-expired-auth` | `45 3 * * *` (systemd timer on serwerek) | Deletes expired `Session` and `Verification` rows (`pruneExpiredAuthRecords()`, `lib/auth/prune-expired.ts`) |
| `/api/cron/retention` | `15 4 * * *` (systemd timer on serwerek) | Clears IP/user agent older than 90 days (`anonymizeOldTechnicalData()`, `lib/modules/privacy/`) and retries queued Resend contact removals (`processContactRemovals()`) |
| `/api/cron/sync-public-thumbnails` | `0 6 * * *` (registered; daily works on Hobby) | Safety net for R2 thumbnail sync: makes the public thumbnail bucket hold exactly the published videos' thumbnails (`reconcilePublicThumbnails()`, see §4.8). No-op until the public bucket/host env vars are set |


**`prune-playback-sessions` (added 2026-09-20):** `AppPreloadProvider`'s hover/idle prefetch creates a real `VideoPlaybackSession` row via the same `PlaybackService.createPlaybackPlanWithContext` path as actual playback, for every preloaded video regardless of whether the viewer ever plays it — so the table grows with page traffic, not just views. This cron deletes rows older than `STALE_PLAYBACK_SESSION_RETENTION_DAYS` (30) where `countedAsView` is still `false`; it never touches a session that was ever counted as a real view, and never touches `countedAsView`/aggregated view-count logic elsewhere. Confirmed before adding this: no admin diagnostics, patron read model, or Stripe dispute logic reads `VideoPlaybackSession` — it's pure telemetry with no downstream consumer that needs long retention. `VideoPlaybackEvent.session` is `onDelete: SetNull`, so deleting a session never cascades into deleting its events; they just lose the session link.
