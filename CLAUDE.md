## 4. Critical Invariants — Read Before Editing

**Update 2026-09-26 (schema/migration drift reconciled):** an audit found `schema.prisma` had silently diverged from what the full migration history actually builds — 7 indexes and several nullable/default changes declared in the schema with no migration ever creating them, plus two `Notification*` foreign keys missing `ON UPDATE CASCADE` that every other relation has. Confirmed via a from-scratch `prisma migrate deploy` + `prisma migrate diff` replay (no production DB access in this environment) and fixed with three new, additive-only migrations: `20260926120000_add_missing_schema_indexes`, `20260926120001_reconcile_notification_fk_onupdate`, `20260926120002_reconcile_schema_nullable_default_drift` (the last one backfills any pre-existing NULL `VideoPlaybackSession.maxProgressMs` to `0` before tightening it to `NOT NULL`, since `playback.service.ts`'s `videoPlaybackSession.create()` calls have always omitted that field in reliance on a DB default that didn't actually exist). A from-scratch replay now produces zero diff against `schema.prisma`. Full writeup: `docs/audit/2026-09-26-prisma-migration-drift-and-timestamp-audit.md` (also covers a separate, no-code-change audit of duplicate migration timestamps — `PRISMA-MIGRATION-TIMESTAMP-DEDUP-001` — which remains a historical/documentation finding only, since renaming an already-applied migration folder would break `_prisma_migrations` tracking on any environment that has it applied).

**Migrations run only on production builds (2026-09-30):** `vercel-build` is `node scripts/vercel-build.mjs`; it runs `db:migrate:repair` + `db:migrate:deploy` only when `VERCEL_ENV` is not `preview`/`development`. Before this, every PR preview build applied its migrations to the **same Neon database as production** (the preview env shares `DATABASE_URL`). On 2026-09-30 a migration file that started with a UTF-8 BOM failed that way from a PR preview, left a failed row in `_prisma_migrations` and blocked every later deploy until it was marked rolled back (`rolled_back_at`, same as `prisma migrate resolve --rolled-back`; the repo's repair script only auto-repairs names in its `ROLLBACK_SAFE_FAILED_MIGRATIONS` allowlist). Rules: write migration files **without a BOM** (the `integration-postgres` CI job now catches it), keep them additive/idempotent, and expect PR previews to run against the production schema without the PR's new columns.

### 4.1 Patron Status Source of Truth

**`PatronGrant` table is the sole source of patron/supporter bookkeeping** — but as of 2026-09-22 it **no longer gates video access** (see §4.4). It still exists, is still created by `fulfillPayment()`, and is still what any "is this user a supporter" read (admin diagnostics, email audience, decorative UI badges) should query. A user is recorded as having supported iff:

```prisma
patronGrants: { some: { revokedAt: null } }
```

- `User.isPatron`, `User.patronSince`, `User.patronSource` fields **do not exist** (removed in migration `20260630000000_remove_legacy_user_patron_cache`).
- Never write patron status to the `User` table. Never read it from there.
- `recalculatePatronStatus()` is a pure read — it computes status from active grants, no writes.
- DTO/UI fields named `isPatron` may exist only as derived/decorative values computed from grants or admin role.
- **Do not reintroduce a `PatronGrant`/`getPatronStatus()` check inside `checkVideoAccess()`** without an explicit owner decision to revert the 2026-09-22 non-commercial model — that would silently repaywall content the current Regulamin promises is free.

### 4.2 Patron Grant Lifecycle

```txt
Stripe webhook (signature verified)
  → record StripeEvent
  → record Payment (financial fact)
  → Patron eligibility policy (amount ≥ threshold)
  → fulfillPayment() — canonical, replay-safe
      → creates PatronGrant
      → sends confirmation email
```

`fulfillPayment()` in `lib/modules/payments/` is idempotent and replay-safe. Always use it for payment fulfillment, never issue manual `updateMany({ status: 'SUCCEEDED' })` shortcuts. **This lifecycle is unchanged by the 2026-09-22 access-gate removal** — a qualifying payment still creates a `PatronGrant` record (useful supporter bookkeeping/decorative badge), it just no longer unlocks anything that sign-in alone didn't already unlock.

**Return-page fast path (added 2026-07-21):** the webhook remains the reliability backbone, but `getOwnedPaymentStatus()` (`lib/modules/payments/application/get-payment-status.use-case.ts`, backing `GET /api/payments/[paymentId]`) no longer only reads the local `Payment.status`. When the caller's own payment (ownership already enforced by the `{ id, userId }` lookup) is still `PENDING` and has a `stripeIntentId`, it retrieves that PaymentIntent directly from Stripe and, if Stripe already reports `succeeded`, calls `fulfillPayment()` right there — the same canonical, replay-safe path, never a manual status write — before responding. This is what lets `DonationBox.tsx`'s post-checkout success screen resolve near-instantly instead of only after the webhook lands; the polling loop there does an immediate check on mount rather than waiting for the first interval tick. Any Stripe/network failure in this path is swallowed and falls back to the normal webhook-driven polling — it is a best-effort fast path, not a new source of truth.

**Return-page message trusts Stripe's redirect signal.** `DonationBox.tsx` reads Stripe's own `redirect_status` off the return URL: `succeeded` (or the param being absent on a plain card confirmation) shows the full thank-you immediately; `failed` shows a red failure header (`CheckoutModal.tsx` renders a red ✕ + "something went wrong" for `FAILED_CANCELED`/`REFUNDED_DISPUTED`); genuinely async `pending`/`processing` methods get a neutral processing screen until the background reconciliation confirms. The reconciliation loop only ever *upgrades* a processing screen to success — it must never downgrade an already-shown success message, and no raw `PaymentUiStatus` enum or "webhook" jargon may reach the UI. Closing the success screen (X or "back to site") after a succeeded payment does a full `window.location` reload to the clean URL so every server-rendered surface (Patron badge, `viewerIsPatron` video locks, support-box copy) comes back reflecting the freshly-granted access at once — do not downgrade this to a soft `router.replace`, which leaves stale non-patron server state and cached playback plans.

### 4.3 Video Playback Security

- **Never expose `videoUrl` to the public frontend.** Use `PublicVideoDTO` for all public-facing data.
- The only playback path is the own-HLS plan from `/api/media-source/[videoId]` (`PlaybackService` → `buildSelfHlsPlan()`). The old `/api/media/[...path]` proxy, `Video.videoUrl` playback, embeds (YouTube/Vimeo) and provider signing (Mux/Cloudflare Stream) no longer exist; `Video.videoUrl` is a dead legacy column that nothing reads or writes. `MediaPolicy.isProbablyRawMediaUrl()` stays as a safety net: a raw storage/provider URL in a plan is dropped by `/api/media-source` (plan becomes not playable).
- `PlaybackPlan` from the access module gates all player mounting: `READY` → mount player, any denied state → locked placeholder.
- Never mount a player, fetch streams, request tokens, resolve the playback source, or log views for a denied plan.
- Rows of any provider other than `SELF_HLS` (leftover Mux/Cloudflare Stream/YouTube/Vimeo/R2/S3/Blob assets or routes) are ignored by `PlaybackService` (never crash, never played, no URL/id in the plan); publication blockers (`VideoPolicy`) and `VideoPlaybackRouteService.activateRoute()` accept only `SELF_HLS`.
- **Never CDN-cache `/api/media-source` responses** (no `s-maxage`/`public` Cache-Control). The response carries a per-viewer `playbackSessionId` bound to the requester fingerprint.

### 4.9 Comment Reactions

- `CommentReactionType` enum is `LIKE | DISLIKE` (one reaction per user per comment via `@@unique([userId, commentId])`).
- Dislike has **no public counter** — only `likesCount` is aggregated; deleting/replacing a DISLIKE must never touch `likesCount`.
- Reactions are a target state, not a toggle: `setCommentReaction` / `setVideoReaction` (`LIKE`, `DISLIKE` or `null`), idempotent and race-safe (`createMany({ skipDuplicates })`, counters move by affected row counts). API: `PUT /api/comments/[id]/reaction` with optional body `{ type: "LIKE" | "DISLIKE" }`, `DELETE` clears (60/min per user). Video likes: server action `setVideoReaction` in `lib/actions/interactions.ts`, which must never `revalidatePath` (Hero updates its own state from the result).
- Visibility: `mapCommentToDto` is a whitelist. Text and author are returned only for `VISIBLE`; moderators also see `HIDDEN`/`HELD_FOR_REVIEW`; `DELETED` content stays in the database but is shown only in the admin panel and never when the author deleted it; the text of author-deleted comments is erased after 30 days by `/api/cron/purge-deleted-comments` (moderation-deleted/hidden text is kept). `threadCommentWhere()` in the repository is the one list filter (also hides comments of deleted accounts). `repliesCount` in DTOs is computed (`_count`), the `Comment.repliesCount`/`score`/`imageUrl` columns are no longer read or written.
- No supporter ("Patron") distinction anywhere public (owner decision 2026-10-04: a tip buys nothing, not even a badge): comment DTOs carry only `ADMIN`/`AUTHOR` badges, the UI shows only "Twórca" (video creator), no avatar ring. Patron status is visible in the admin panel only.
- Moderation is a state machine in `CommentPolicy` (`restore` only from `HIDDEN`/`HELD_FOR_REVIEW`; `DELETED` is final); a disallowed action is `CONFLICT` (409). Every comments route maps errors through `commentErrorStatus` / `lib/api/comment-response.ts`; database messages never reach the client (`commentDatabaseError`).
- Reports: one per user and comment; `reportsCount` = pending reports (recomputed on report and on resolve); 3 pending reports hold a viewer's comment for review, never one by an admin or the video's creator.
- Threads: the list embeds the first 3 replies; the rest is paged through `GET /api/comments/[id]/replies` (public, also for guests).

**Update 2026-09-20 (separate withdrawal-right waiver checkbox — art. 38(1)(13) Polish Consumer Rights Act):** every checkout surface (`DonationBox`, `SecretPledgeBox`, `SecretPledgeBox2`) now requires a **second, distinct** checkbox alongside the existing Terms/Privacy checkbox before `submit()` will proceed. **Flag (2026-09-22, resolved same day — see the entry immediately below):** the new Regulamin/Terms text (see the "major" 2026-09-22 entry near the top of this file) reframes support as a non-refundable gift that is explicitly **not** a sale of digital content and grants no access — the exact premise art. 38(1)(13)'s withdrawal-right waiver applies to. **Update 2026-09-22 (withdrawal checkbox removed — the question above is resolved):** the owner asked directly whether this checkbox is still needed, and specifically to check a Polish Supreme Administrative Court (NSA) ruling on streamer "donejty" from roughly two months earlier: **NSA, 7 July 2026, case III FSK 113/26.** That ruling (a tax case, on whether anonymous streamer donations count as tax-exempt `darowizna`/gift rather than taxable income) sets the test for gift status: known amount, paid from the donor's own assets, **completely gratuitous, with no reciprocal benefit whatsoever** — the court and commentary are explicit that *any* benefit granted in exchange (their own example: access to extra content) disqualifies the payment from gift treatment. Put together: (1) the 2026-09-22 access-gate removal (§4.4/§4.10 above) already made support grant literally nothing, which is exactly what this ruling requires for gift/tax-exempt treatment — so that change was legally load-bearing, not just a UX one; and (2) once there is truly no reciprocal benefit, this checkbox's own legal basis (a sale-of-digital-content contract to waive withdrawal from) no longer exists — keeping consumer-sale language like "prawo odstąpienia od umowy" around a transaction that must read as a pure gift actively cuts against the "nic nie otrzymuje w zamian" test the ruling turns on. The checkbox, its state (`isWithdrawalAcknowledged`/`showWithdrawalError`/`onWithdrawalCheckedChange` in `useCheckoutFlow.ts`), its `submit()` gate, and its `t.acceptWithdrawal`/`t.pleaseAcceptWithdrawal` translation strings were removed from all three checkout surfaces (`DonationBox`, `SecretPledgeBox`, `SecretPledgeBox2`) and from `useCheckoutFlow.ts`/`LanguageContext.tsx`. The ordinary Terms/Privacy checkbox is unchanged and still required. **This is not a substitute for the owner/a lawyer independently verifying the ruling and its application** — it's an AI agent's reading of publicly available legal commentary, done because the owner explicitly delegated the decision in-thread; flag it for a real legal review if the donation model is ever scrutinized. `tests/unit/hooks/useCheckoutFlow.test.tsx` and `tests/unit/components/channel/DonationBox.test.tsx` still assert the removed checkbox's behavior and need updating (same test-debt category as the access-gate change above — no test runner in this environment to verify against).

### 4.12 Auth: Better Auth (2026-10-02, replaces Clerk)

Full write-up: `docs/architecture/auth-better-auth.md`. Rules to keep:

- **Library and data.** `better-auth` with the Prisma adapter on our Postgres. Our `User` model is the Better Auth user (`name` = nickname, `image` <-> `imageUrl`, plus `emailVerified`, `twoFactorEnabled`, `onboardingPending`); extra tables `Session`, `Account`, `Verification`, `TwoFactor` (migration `20261002100000_add_better_auth`, additive). `ClerkEvent` is a dead table kept only because migrations are additive. The `admin` plugin is deliberately not used; roles stay `User.role`.
- **One identity entry point.** Server: `lib/auth/server.ts` (`auth()`, `getAuth(req)`, `currentUser()`) and `lib/api/auth.ts` (`getActorFromAuth`, `requireAdminActor`: DB-backed actor, soft-deleted users rejected). Client: `lib/auth/client.ts` (`authClient`) and `lib/auth/react.ts` (`useAuth`, `useUser`, same shape the components used). Do not import `better-auth` anywhere else in app code; do not add a second get-or-create-user path (Better Auth creates the row; `getOrCreateCurrentUser()` only loads it and fails closed).
- **Admin** = `User.role = ADMIN`. Bootstrap by `ADMIN_EMAILS` (a verified e-mail is promoted on actor resolution, audited as `AUTH_ADMIN_BOOTSTRAP`; a never-verified address is never promoted). The check runs on every request, so empty the variable after the first sign-in (a demotion is otherwise undone) and never list a shared inbox. `ADMIN_CLERK_USER_IDS` is gone.
- **Methods.** E-mail + password (min 10 chars, no composition rules, haveIBeenPwned in production, `requireEmailVerification`, `autoSignIn` off; sign-up with an existing e-mail answers `EMAIL_TAKEN`, see below), Google (redirect + One Tap, `account.accountLinking.trustedProviders: ["google"]` so a Google sign-in links to the existing row with the same e-mail), TOTP two-step (`twoFactor`). Apple and passkeys are not offered (passkeys: not done yet).
- **Existing e-mail at sign-up (owner decision 2026-10-02: convenience over privacy, enumeration accepted).** Sign-up with an address that already has an account returns 422 `EMAIL_TAKEN` (`EMAIL_TAKEN_GOOGLE` if it only has a Google link); the modal shows "this e-mail already has an account" with Sign in / Forgot password actions. Implemented as an AFTER hook (`rejectExistingEmailSignUp` in `lib/auth/hooks.ts`) because `options.hooks.before` runs before the captcha plugin; do not move it to a before hook, or Turnstile is bypassed. Sign-in and password reset stay enumeration-safe. The "account exists" e-mail was removed.
- **Protection.** Cloudflare Turnstile on sign-up/sign-in/reset/resend (`CAPTCHA_ENDPOINTS` in `lib/auth/config.ts`; the widget gets its site key at runtime through `AuthPublicConfigProvider` and renders `interaction-only`: invisible and out of layout unless a challenge is needed, button spinner while it runs); Better Auth rate limits on our Redis REST store via `customStorage.consume` (`lib/auth/rate-limit-storage.ts`) plus a per-e-mail sign-in lockout (10 per 15 min); secure/HttpOnly/SameSite=Lax cookies with prefix `pp`; password change and reset revoke other sessions; audit events `AUTH_SIGN_UP/IN/OUT`, `AUTH_PASSWORD_CHANGED`, `AUTH_ADMIN_BOOTSTRAP`, `USER_NICKNAME_CHANGED` (ids only, never secrets).
- **Pre-hijack guard.** If a verified provider is linked to an account whose e-mail was never verified, its password and sessions are deleted (`beforeAccountCreate` in `lib/auth/hooks.ts`). Keep it. Google linking is allowed onto an unverified row (`requireLocalEmailVerified: false`, audit F-04) precisely because of this guard; never-verified password sign-ups are pruned after 7 days by `/api/cron/prune-unverified-accounts`.
- **Audit follow-ups (2026-10-02, `docs/audit/2026-10-02-auth-flows-audit.md`).** Return path `?next=` works (same-site relative paths only); verification-link results are shown (`?verified=1` / `?error=TOKEN_EXPIRED|INVALID_TOKEN`, handled in `AuthModalProvider`); sign-in lockout counts only failed attempts keyed per e-mail + IP; `freshAge` stays 1 day and stale sessions get a "sign in again" prompt (`SESSION_NOT_FRESH`); "remember this device" for 2FA is opt-in (7 days) and 2FA does not apply to Google/One Tap (decision); backup codes can be regenerated; One Tap shows once a day after the entry gate; account deletion needs the password (or a Google sign-in from the last 10 min) and refuses to delete the last admin; legacy accounts with a missing/invalid/duplicate nickname go through onboarding at next sign-in.
- **Proxy.** `middleware.ts` has no auth library call: it keeps the public-route list, CSRF (`/api/admin/*` and `/api/user/*`), admin rate limits, the cron/webhook exemptions and the CSP, and gates the rest with an optimistic session-cookie check (`getSessionCookie`). Missing cookie: API paths get JSON 401, pages are redirected to `/?signin=1&next=...` (the modal opens). The cookie is never proof of identity; real validation is in server code. `/api/auth(.*)`, `/reset-password` and `/sso-callback` are public and exempt from the `/pl` rewrite.
- **Nickname.** Chosen only in the first-sign-in dialog (never in the sign-up form): 3-30 chars (`lib/auth/nickname.ts`), checked for case-insensitive uniqueness by `GET /api/users/nickname-available` (public, per-IP limited) and again server-side (`completeOnboarding`, `updateNickname`). The database enforces it for active, onboarded accounts (partial unique index `User_name_lower_active_key` on `lower(name)`, migration `20261003200000`; a lost race answers `NICKNAME_TAKEN`). Placeholders of accounts in onboarding reserve nothing, and such an account cannot comment or react (`Actor.onboardingPending`, `CommentPolicy`, code `ONBOARDING_REQUIRED`). Edits go through `PATCH /api/user/nickname`; Better Auth's `/update-user` is disabled.
- **Avatar.** New accounts get `public/default-avatar.jpg` (also for Google users, by design). A chosen file is resized to 256 px in the browser (`lib/auth/avatar-client.ts`), validated server side (`validateAvatarDataUrl`) and stored as bytes in the `UserAvatar` table; `User.imageUrl` points at the public `/api/avatars/[userId]?v=...` route (`PUT /api/user/avatar`; `SafeAvatar` renders it unoptimized). Legacy rows may still reference `img.clerk.com`, which stays in the CSP `img-src`.
- **First sign-in (Google and e-mail).** Every new account gets a placeholder name (e-mail local part) and `onboardingPending = true`; `OnboardingDialog` (mounted in `AuthModalProvider`, cannot be dismissed) asks for the nickname and an optional avatar, then `POST /api/user/first-sign-in` sets them and sends the welcome e-mail. This is the only place the welcome e-mail is sent (exactly once). The sign-up form asks e-mail, password and "Repeat password" only.
- **E-mails.** Verification, reset and password-changed mails go through the existing Resend module and `EMAIL_DEFAULTS`/`EmailTemplate` (slugs `verify-email`, `reset-password`, `password-changed`, `welcome-email`, and for an e-mail change `change-email-confirm`, `change-email-verify`, `email-changed`), localized by `User.language`, without a marketing unsubscribe link, fire-and-forget (no timing leak). A DB template saved in `/admin/emails` wins over the default.
- **E-mail change.** Needs the password (or a Google sign-in from the last 10 min) in the `/change-email` body (`guardChangeEmail` before hook, 5/h per user), is approved from the CURRENT address first, then verified on the new one, and the old address is notified (`AUTH_EMAIL_CHANGED`). Reset/verification mails are also limited per target address. Auth rate-limit counters fail open with an error log when Redis is down (1.5 s timeout), a deliberate choice documented in `lib/auth/rate-limit-storage.ts`.
- **Return pages.** `/sso-callback` (Google return: must never render blank, 8 s fallback link; return path in `sessionStorage` via `lib/auth/sso-return.ts`) and `/reset-password` (e-mail link target, `?token=` or `?error=INVALID_TOKEN`).
- **Language.** Stored in `User.language` (the database is the only copy); `AuthLifecycleProvider` syncs it once per login and persists changes through `PATCH /api/user/language`.
- **Account deletion.** `DELETE /api/user/account`: our anonymising cleanup, then sessions/accounts/two-factor rows are deleted; the row stays as a tombstone and cannot sign in again.
- **Secrets.** `BETTER_AUTH_SECRET` (>= 32 chars, required in production; rotating it signs everyone out and breaks stored TOTP secrets AND backup codes, so 2FA accounts are locked out: follow the procedure in `docs/architecture/auth-better-auth.md`), `GOOGLE_CLIENT_ID/SECRET`, `TURNSTILE_SITE_KEY/SECRET_KEY`, `ADMIN_EMAILS`, optional `BETTER_AUTH_URL`, `BETTER_AUTH_TRUSTED_ORIGINS`. Google redirect URI per host: `<origin>/api/auth/callback/google`.

### 4.15 Premieres (scheduled release, 2026-09-30)

### 4.17 Own HLS delivery: the only video source (2026-10-02)

`StorageProvider.SELF_HLS` plays video from our own HLS: encoded by `scripts/hls/encode-hls.mjs`, stored in the private R2 bucket `polutek-hls`, delivered by the Cloudflare Worker `workers/hls-edge` on `video.pawelperfect.com` (Free plan). Rules: the delivery token (`SelfHlsTokenService`, HMAC over `<videoId>/<version>/<exp>`, in the URL path) is issued **only** by `PlaybackService` after `checkVideoAccess()` and the premiere gate, via `buildSelfHlsPlan()`; a denied plan carries no URL (tested). There is no fallback to another provider: without `HLS_TOKEN_SECRET`, or when the own-HLS asset is not READY, the plan is `ERROR`/`PROCESSING`/`NO_PRIMARY_ASSET` with no URL, token or session, and `VideoPlayer` plays only `source.kind = self_hls` (an https `.m3u8`). Manual route activation: `scripts/hls/activate-self-hls.sql` (normally the worker does it). It is access control, not DRM. **All three videos (`czesc`, `jj`, `dla-patronow`) are served from own HLS.** Player: hls.js is a pinned npm dependency (`hls.js/light`) loaded from our own bundle via `provider.library` (`app/components/player/self-hls.ts`); never the Vidstack CDN default, no `cdn.jsdelivr.net` in CSP. Token renewal never remounts the player: `PremiumWrapper.renewPlaybackPlan()` re-fetches `/api/media-source/<id>?session=<id>` (full access check; the server keeps the viewer's own playback session) and hls.js rewrites every request to the newest token (`xhrSetup`). The old provider routes (`PREVIOUS`) and the other legacy rows stay in the DB and are ignored by the code (deleting them is a separate cleanup PR). The `StorageProvider` enum values other than `SELF_HLS` and the tables `VideoDistributionPlan/Target`, `VideoProviderJob`, `VideoProviderWebhookEvent` are LEGACY in `schema.prisma` (migration history stays additive; do not drop them without an owner decision, do not write them). Details: `docs/operations/HLS-SELF-HOSTED.md`, `docs/architecture/self-hosted-hls.md`.

**Own upload + encode pipeline (2026-10-03):** decision 2026-10-02: no third-party video providers (Mux, Cloudflare Stream, Vimeo, YouTube); `SELF_HLS` is the only source (the provider code — Mux, Cloudflare Stream, YouTube, Vimeo, distribution plans/jobs, webhooks, reconcile cron, `/api/media` proxy — was removed on 2026-10-02; never reintroduce a second provider without an explicit owner decision). Admin uploads the ORIGINAL straight to the private R2 bucket `polutek` (presigned multipart, resumable; server verifies size and magic bytes at `complete`, deletes bad files), `completeOriginalMultipart` queues a `VideoEncodeJob` (Postgres, `SELECT ... FOR UPDATE SKIP LOCKED`, one encode at a time, retries with backoff, heartbeat, cancel, re-encode; no pg-boss/Redis). The worker is the separate container `encoder` (`scripts/video-worker.ts`, `lib/modules/video-pipeline/`, image target `worker`): download, ffprobe limits, `encodeHls()`, upload to `polutek-hls` with `master.m3u8` last, verify, only then `VideoAsset(SELF_HLS, READY)` + active route + optional auto-publish; failures/cancel delete the partial prefix. Never run encoding in the Next.js request path. Publication blockers accept only `SELF_HLS`. Everything (flows, ops, debugging, rollback, server enable commands): `docs/operations/VIDEO-PIPELINE.md`.

- **CSRF:** every POST/PUT/PATCH/DELETE under `/api/admin` is checked centrally in `middleware.ts` via `lib/api/csrf.ts` (`assertSameOrigin`), before `auth.protect()`. - **Rate limits:** `lib/api/admin-rate-limit.ts`, run in the same middleware after auth, keyed by admin user id and IP (Upstash; both checks in parallel, 700 ms timeout, fails open on error/timeout). Defaults 120/min for reads and mutations; strict limits: refund 5, dispute-sync 5, emails/broadcast 3, notifications/broadcast 3, users/[id]/patron 10, payment-settings 10. - **Break-glass token:** `HEALTHCHECK_TOKEN` is accepted only in the `x-health-token` header (`lib/api/health-token.ts`, constant-time compare, Edge-safe). The `?token=` query and the old `x-healthcheck-token`/`x-diagnostics-token` headers were removed. `/api/admin/health/clerk` still skips `auth.protect()` only when that header matches.

### 5.2 Shared admin list-query scaffold (2026-09-26)

Resolved (partially — see the videos exception below) `ADMIN-LIST-SCAFFOLD-CONSOLIDATION-001`. `lib/admin/use-admin-list-query.ts` is a shared client-side hook (`useAdminListQuery<TItem>()`) that owns the page/total/totalPages/items/isLoading/error state and the fetch-try-catch-parse-error boilerplate that used to be independently duplicated across list pages. It deliberately does **not** own filter state or URL construction — each page keeps its own filter state and builds its own request URL, then calls the hook's `fetchPage(url, targetPage, { fallbackMessage })`; the hook returns the raw parsed response body on success so callers can pull out page-specific extra fields (stats, summary) themselves. This narrow scope (state/fetch bookkeeping only, not a full data-table component) was a deliberate choice to keep the migration low-risk given the "no list may lose existing functionality" constraint — no API contract changed.

Migrated to `useAdminListQuery`: `app/admin/comments/reports/page.tsx`, `app/admin/comments/page.tsx` (search/videoId filters and bulk-selection state stayed local), `app/admin/users/page.tsx` (all its filters stayed local; a stray no-op `setPage(1)` call on the patron-source filter was removed as dead code — the page-1 reset already happens via the filter-change `useEffect` calling `fetchUsers(1)`).

**`app/admin/videos/components/useAdminVideos.ts` was deliberately NOT migrated.** Its `fetchVideos()` has three behaviors the generic hook doesn't (and shouldn't be extended to) support: (1) a 401/403 response sets a distinct "Brak uprawnień administratora." message rather than the generic load-error fallback — the shared hook only sees `res.ok`, not the status code; (2) `stats` is extracted from the same response body and stored separately; (3) `isRefetching` is only set around calls that explicitly pass `{ pending: true }` (initial load and background/no-pending calls leave it `false`), which `VideoTableWrapper.tsx` relies on to distinguish the initial full-skeleton state from a background refetch overlay — the shared hook's `isLoading` is unconditionally true for every call, which would have made both states fire together on first load. Reusing the hook here would have meant either losing one of these three behaviors or extending the hook with video-specific escape hatches, both of which cut against the hook's whole point. `useAdminVideos` already is videos' single, non-duplicated list/fetch implementation (nothing else reimplements it), so there was no duplication left to consolidate there — only `readVideoLoadError` (see below) was actually duplicated code, and that's fixed.

**`readVideoLoadError`/`readAdminApiError` duplicate merged**: the local `readVideoLoadError` in `useAdminVideos.ts` was removed; it now imports the shared `readAdminApiError` from `lib/admin/api-error.ts` (moved there via `git mv` from `app/admin/videos/components/api-error.ts`, content unchanged — import paths in `videos/page.tsx`, `videos/[id]/edit/page.tsx`, `videos/[id]/page.tsx` and `tests/unit/admin-api-error.test.ts` updated accordingly).

## 6. Cron Jobs


**Update 2026-09-29:** `/api/cron/(.*)` is a public route in `middleware.ts` (each handler authorizes itself with `Bearer $CRON_SECRET` and returns 401 when the secret is missing). Before this, the routes were not listed there, so Vercel Cron (no Clerk session) hit `auth.protect()` and got the site's HTML page (HTTP 200) instead of the handler: every cron silently did nothing. `CRON_SECRET` must be set in Vercel Production. `tests/unit/security/cron-routes-reach-handler.test.ts` guards both halves. To check a cron from outside: without the token it must return 401 JSON, not HTML.

|---|---|---|
| `/api/cron/stripe-reconciliation` | `*/15 * * * *` | Recovers stuck `PENDING` payments by re-running `fulfillPayment()` or marking as failed |
| `/api/cron/prune-playback-sessions` | `0 5 * * *` (registered; daily works on Hobby) | Deletes `VideoPlaybackSession` rows older than 30 days that were never counted as a view (`pruneStalePlaybackSessions()`, `lib/modules/video/`) |

**`prune-playback-sessions` (added 2026-09-20):** `AppPreloadProvider`'s hover/idle prefetch creates a real `VideoPlaybackSession` row via the same `PlaybackService.createPlaybackPlanWithContext` path as actual playback, for every preloaded video regardless of whether the viewer ever plays it — so the table grows with page traffic, not just views. This cron deletes rows older than `STALE_PLAYBACK_SESSION_RETENTION_DAYS` (30) where `countedAsView` is still `false`; it never touches a session that was ever counted as a real view, and never touches `countedAsView`/aggregated view-count logic elsewhere. Confirmed before adding this: no admin diagnostics, patron read model, or Stripe dispute logic reads `VideoPlaybackSession` — it's pure telemetry with no downstream consumer that needs long retention. `VideoPlaybackEvent.session` is `onDelete: SetNull`, so deleting a session never cascades into deleting its events; they just lose the session link.
